# LAB 6: BFF Features in NestJS

## Overview

В лабораторной работе №6 в проект `BeerCinema` были добавлены механизмы NestJS для работы с запросами и ответами:

- измерение времени обработки запроса через interceptor;
- клиентское кэширование через `ETag` и `Cache-Control`;
- серверное in-memory кэширование через `CacheModule`;
- загрузка файлов в Yandex Object Storage;
- поддержка загрузки постеров как в MVC-формах, так и в REST API.

Ниже перечислено, что именно было сделано, в каких файлах и зачем.

## 1. Install Dependencies

Для ЛР6 были добавлены зависимости:

- `@nestjs/cache-manager`
- `cache-manager`
- `@aws-sdk/client-s3`
- `@aws-sdk/lib-storage`
- `@types/multer` (dev dependency)

Они используются для:

- серверного кэша ответов REST API;
- загрузки файлов в S3-совместимое хранилище;
- поддержки `multipart/form-data` и `Express.Multer.File`.

## 2. Create TimingInterceptor

Файл: [src/common/interceptors/timing.interceptor.ts](../src/common/interceptors/timing.interceptor.ts)

Что реализовано:

- создан interceptor `TimingInterceptor`;
- в начале обработки запроса сохраняется `Date.now()`;
- после получения результата вычисляется затраченное время;
- в консоль выводится лог в формате:
  - `[Timing] ClassName.method: Xms`

Логика работы по типам запросов:

- для REST и GraphQL в ответ добавляется заголовок `X-Elapsed-Time`;
- для MVC-роутов с `@Render()` в шаблонный контекст добавляется поле `serverElapsed`.

Почему это нужно:

- лабораторная требует измерять время обработки запроса;
- время должно не только логироваться, но и возвращаться клиенту;
- для шаблонов время сервера должно отображаться прямо на странице.

## 3. Create ETagInterceptor

Файл: [src/common/interceptors/etag.interceptor.ts](../src/common/interceptors/etag.interceptor.ts)

Что реализовано:

- создан interceptor `ETagInterceptor`;
- interceptor работает только для HTTP `GET` запросов;
- тело ответа сериализуется в JSON;
- на основе JSON строится SHA1-хэш;
- полученный хэш записывается в заголовок `ETag`.

Дополнительная логика:

- если клиент присылает заголовок `If-None-Match`;
- и значение совпадает с вычисленным `ETag`;
- сервер возвращает `304 Not Modified`;
- тело ответа не отправляется, используется `EMPTY` из RxJS.

Почему это нужно:

- это часть клиентского кэширования;
- если ресурс не изменился, клиенту не нужно получать его заново целиком.

## 4. Create StorageModule and StorageService

Файлы:

- [src/storage/storage.module.ts](../src/storage/storage.module.ts)
- [src/storage/storage.service.ts](../src/storage/storage.service.ts)

Что реализовано:

- создан отдельный инфраструктурный модуль `StorageModule`;
- создан сервис `StorageService`;
- внутри `StorageService` настроен `S3Client` для Yandex Object Storage:
  - endpoint: `https://storage.yandexcloud.net`
  - region: `ru-central1`
  - credentials берутся из переменных окружения

Метод `upload(file)`:

- принимает `Express.Multer.File`;
- генерирует уникальный ключ в папке `films/`;
- загружает файл в бакет через `PutObjectCommand`;
- возвращает публичный URL загруженного файла.

Используемые env-переменные:

```env
YANDEX_ACCESS_KEY_ID=...
YANDEX_SECRET_ACCESS_KEY=...
YANDEX_BUCKET=beer-cinema
```

Почему это нужно:

- по условию ЛР файлы должны загружаться не по готовой ссылке вручную, а в объектное хранилище;
- отдельный модуль изолирует инфраструктурную логику и переиспользуется в нужных местах.

Дополнительно в `StorageService` были добавлены:

- `uploadBuffer(...)` для загрузки уже существующих локальных файлов в бакет;
- `deleteByUrl(...)` для удаления объектов из бакета по URL, если они относятся к нашему бакету.

## 5. Update app.module.ts with APP_INTERCEPTOR

Что изменено:

Что это даёт:

## 7. Update films.api.controller.ts

Файл: [src/films/films.api.controller.ts](../src/films/films.api.controller.ts)

### 7.1. Подключение ETagInterceptor

На весь `FilmsApiController` добавлено:

```ts
@UseInterceptors(ETagInterceptor)
```

Это значит:

- все `GET`-ответы этого контроллера получают `ETag`;
- при совпадении `If-None-Match` может вернуться `304`.

### 7.2. Серверный кэш для GET /api/films и GET /api/films/:id

На методы `findAll()` и `findOne()` добавлено:

```ts
@UseInterceptors(CacheInterceptor)
@Header('Cache-Control', 'public, max-age=3600')
```

Что это даёт:

- `CacheInterceptor` кэширует ответы на сервере;
- `Cache-Control` сообщает клиенту, что ресурс можно кэшировать в течение часа.

Дополнительно:

- `GET /api/films` продолжает возвращать пагинацию;
- также формируется заголовок `Link` для `prev` / `next`.

### 7.3. Новый endpoint для загрузки постера

Добавлен endpoint:

```ts
POST /api/films/:id/poster
```

Что он делает:

- принимает `multipart/form-data`;
- использует `FileInterceptor('file')`;
- валидирует файл через `ParseFilePipe`:
  - максимум `5 MB`
  - только `jpeg`, `png`, `webp`
- загружает файл через `StorageService`;
- обновляет `posterUrl` у фильма через `filmsService.update(...)`.

Почему это важно:

- по условию ЛР нужна работа с файлами и REST API;
- это отдельный API-способ загрузки постера, помимо MVC-форм.

### 7.4. Удаление старого постера из бакета

После доработки сервиса фильмов реализованы два дополнительных сценария:

- при обновлении постера старый объект удаляется из бакета, если он хранился в нашем Object Storage;
- при удалении фильма связанный постер тоже удаляется из бакета.

Это предотвращает накопление неиспользуемых объектов в хранилище.

## 15. Possible Defense Questions

Ниже собраны вопросы, которые преподаватель может задать на защите ЛР6, и короткие ответы, опирающиеся на реализованный код.

### 15.1. Как проверить, что всё работает?

Нужно показать:

- `X-Elapsed-Time` в REST;
- `X-Elapsed-Time` в GraphQL;
- `ETag` в ответе;
- `304 Not Modified` при `If-None-Match`;
- `Cache-Control` на кэшируемых REST endpoint;
- загрузку постера в Yandex Object Storage;
- удаление старого файла из бакета при замене постера или удалении фильма.

Для проверки удобно использовать `curl`, Swagger и браузер.

### 15.2. Почему обязательно нужен `X-Elapsed-Time` для GraphQL?

Потому что по условию ЛР время обработки должно возвращаться клиенту не только для REST, но и для GraphQL.

В проекте это сделано так:

- `TimingInterceptor` проверяет `context.getType<string>() === 'graphql'`;
- через `GqlExecutionContext.create(context)` получает GraphQL context;
- заголовок выставляется в `res.setHeader('X-Elapsed-Time', ...)`.

Чтобы это заработало, в `GraphQLModule` добавлен:

```ts
context: ({ req, res }) => ({ req, res })
```

### 15.3. Чем отличается файловое хранилище от объектного?

Файловое хранилище:

- похоже на обычную файловую систему;
- работает через файлы и директории;
- ориентировано на иерархию каталогов.

Объектное хранилище:

- хранит данные как объекты;
- у каждого объекта есть ключ, содержимое и метаданные;
- "папки" обычно логические, а не настоящие;
- хорошо подходит для картинок, документов, статики, CDN-сценариев.

В этой лабораторной используется именно объектное хранилище:

- бакет `beer-cinema` хранит постеры как объекты;
- ключи объектов выглядят как `films/...`;
- в БД хранится публичный URL на объект.

### 15.4. Что такое бакет и сервисный аккаунт в этой лабе?

Бакет:

- это контейнер в Object Storage;
- именно в нём лежат загруженные постеры.

Сервисный аккаунт:

- это технический аккаунт приложения;
- его static access key используется backend-сервисом для загрузки и удаления файлов в бакете.

Связка такая:

- приложение получает файл;
- `StorageService` подключается к Yandex Object Storage;
- сервисный аккаунт авторизуется ключами;
- файл сохраняется в бакет.

### 15.5. Почему выбран Yandex Object Storage?

Потому что он:

- S3-совместим;
- подходит под требования лабораторной;
- позволяет работать через AWS SDK;
- даёт удобную интеграцию с NestJS backend.

### 15.6. Почему кэшируется именно сущность `films`?

Потому что:

- фильмы читаются чаще всего;
- они редко меняются;
- список фильмов и карточка фильма хорошо подходят для кэширования;
- это даёт понятный и легко демонстрируемый эффект.

### 15.7. Чем отличается клиентское кэширование от серверного?

Клиентское кэширование:

- управляется через `ETag` и `Cache-Control`;
- клиент может не скачивать тело ответа повторно;
- сервер может ответить `304 Not Modified`.

Серверное кэширование:

- хранит результат запроса на сервере в памяти;
- повторный запрос может обслуживаться быстрее;
- в проекте реализовано через `CacheModule` и `CacheInterceptor`.

### 15.8. Почему используется interceptor, а не middleware?

Потому что interceptor:

- работает до и после выполнения handler;
- имеет доступ к результату выполнения контроллера/resolver;
- позволяет модифицировать ответ;
- удобно комбинируется с RxJS.

Middleware больше подходит для предварительной обработки запроса, но не так удобен для работы с итоговым ответом.

### 15.9. Как работает `Observable` / `Observer` в interceptor?

В NestJS `next.handle()` возвращает `Observable`.

Это означает:

- результат handler приходит как поток данных;
- interceptor может встроиться в этот поток;
- через операторы RxJS (`map`, `mergeMap` и т.д.) можно:
  - изменить данные;
  - добавить заголовки;
  - прервать отправку тела ответа.

В этой ЛР:

- `TimingInterceptor` использует `map(...)`, чтобы после получения результата посчитать время и добавить `X-Elapsed-Time`;
- `ETagInterceptor` использует `mergeMap(...)`, чтобы вычислить `ETag`, а при совпадении `If-None-Match` вернуть `EMPTY` и отдать `304`.

### 15.10. Почему в `ETagInterceptor` используется `EMPTY`?

`EMPTY` — это Observable, который завершается без отправки элементов.

В данном случае это позволяет:

- завершить обработку ответа;
- не отправлять JSON-тело повторно;
- оставить только `304 Not Modified`.

### 15.11. Почему для шаблонов время выводится не в заголовке, а в шаблон?

Потому что по условию лабораторной для страниц, которые рендерятся на сервере, время должно быть видно прямо в интерфейсе рядом с клиентским временем.

Поэтому `TimingInterceptor`:

- распознаёт `@Render()` routes;
- добавляет `serverElapsed` в template context;
- `layout.hbs` показывает это значение в timing bar.

### 15.12. Зачем нужен `Cache-Control`, если уже есть `ETag`?

Потому что они решают разные задачи:

- `Cache-Control` говорит клиенту, как долго можно использовать кэш;
- `ETag` позволяет проверить, изменился ли ресурс, и при необходимости получить `304`.

Вместе они дают более эффективное клиентское кэширование.

### 15.13. Почему при подключении Object Storage пришлось работать с env-переменными?

Потому что access key, secret key и имя бакета:

- зависят от окружения;
- не должны хардкодиться в коде;
- являются конфиденциальными данными.

Поэтому они вынесены в:

- локальный `.env`;
- переменные окружения на Render.

### 15.14. Почему старые постеры пришлось мигрировать отдельно?

Потому что часть seed-данных ссылалась на локальные файлы:

```text
/assets/images/...
```

После перехода на Object Storage нужно было:

- загрузить эти файлы в бакет;
- обновить `posterUrl` в БД;
- привести все фильмы к одной схеме хранения.

Для этого был написан отдельный скрипт `npm run migrate:posters`.

### 15.15. Почему при удалении фильма нужно удалять и файл из бакета?

Иначе в Object Storage будут накапливаться неиспользуемые объекты.

Это приводит к:

- "осиротевшим" файлам;
- лишнему расходу места;
- расхождению между данными БД и реальным состоянием хранилища.

Поэтому в проекте теперь реализовано:

- удаление постера при удалении фильма;
- удаление старого постера при замене на новый.
